# Semantic DOM, SEO, AEO, and GEO

This document is the repository contract for public HTML. It applies to people and AI agents creating or changing Astro layouts, pages, MDX content, and components that render content. Its goal is clear, accessible documents that search engines, answer engines, and generative systems can accurately interpret. It does not promise rankings or rich-result eligibility.

## Page contract

`BaseLayout.astro` is the only document shell. It renders the skip link, site `<header>`, one `<main id="contenido">`, site `<footer>`, consent UI, and document metadata. Pages and content components render _inside_ that main landmark; they must not introduce another `<main>`.

Every public page must have:

- exactly one visible `<h1>` describing the page;
- a concise, page-specific title and meta description passed to `BaseLayout`;
- the canonical URL generated by `BaseLayout` from `siteConfig.url` and the route path;
- Open Graph and Twitter metadata supplied by `BaseLayout`, plus a route-specific social image when one is approved; and
- semantic HTML that accurately represents the visible content.

The design-system preview is intentionally `noindex`; it must remain free of structured data. Before launch, set `siteConfig.features.wireframe` to `false`.

## Landmark and component choices

| Element     | Use it for                                                                                                                     | Do not use it for                                                    |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| `<header>`  | Site-wide or section introductory content                                                                                      | A generic styling wrapper                                            |
| `<main>`    | The page's unique primary content; one per document                                                                            | Nested component content                                             |
| `<nav>`     | A group of navigational links, normally a list                                                                                 | A single unrelated link or an action toolbar                         |
| `<article>` | Self-contained content that still makes sense when shared or syndicated: a legal document, post, testimonial, or repeated card | Every visual box                                                     |
| `<section>` | A themed portion of content with its own heading                                                                               | A layout-only wrapper or a headingless visual band                   |
| `<aside>`   | Complementary or tangential content, such as related links or a notice                                                         | Core page content                                                    |
| `<footer>`  | Site or section footer information                                                                                             | A generic bottom-aligned wrapper                                     |
| `<div>`     | Layout, decoration, or grouping with no semantic equivalent                                                                    | Landmarks, list items, cards with standalone meaning, or definitions |

Use `<address>` for an organisation's contact details. Use `<ul>` or `<ol>` for a list of peer items; each item belongs in an `<li>`. Use `<figure>` and `<figcaption>` when an image, chart, or illustration needs a visible caption.

## Headings and answer-oriented writing

One `<h1>` is permitted per public document. Page sections start with `<h2>`; nested sections use `<h3>`, then `<h4>` only when the hierarchy actually needs it. Do not skip from an `h2` to an `h4`, and do not select a heading level for its typography. Use token classes to control appearance instead.

For content intended to answer a user question, use this shape:

```md
## ¿Qué incluye el servicio?

El servicio incluye estrategia, diseño, desarrollo y una guía de entrega.

After the direct answer, add useful qualification, process detail, examples, or links.
```

The question heading and its short answer must be adjacent in the rendered DOM. A heading followed by a visual wrapper, unrelated callout, or several paragraphs before the answer is less clear to readers and machines.

Use the data structure that matches the claim:

```html
<dl>
  <div>
    <dt>Delivery format</dt>
    <dd>Static HTML, CSS, and minimal client-side JavaScript.</dd>
  </div>
</dl>

<table>
  <caption>
    Plan comparison
  </caption>
  <thead>
    <tr>
      <th scope="col">Plan</th>
      <th scope="col">Support</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <th scope="row">Standard</th>
      <td>Email</td>
    </tr>
  </tbody>
</table>
```

Use a list when item order is meaningful (`<ol>`) or when it is not (`<ul>`). Do not turn a card grid into a table unless it is truly tabular.

## Links, buttons, forms, and status

An `<a href="…">` changes location. A `<button type="button">` performs an in-page action such as opening consent preferences. Do not attach JavaScript actions to an anchor, `div`, or `span`; do not use a button for ordinary navigation.

Use native form controls with visible `<label>` elements. Keep a form submission usable without JavaScript. Client enhancement must expose pending, success, and error states through an appropriate live/status region without replacing the native form semantics.

## Images and assets

Prefer Astro's `<Image />` for rendered assets. Give every meaningful image concise alternative text that communicates its purpose; give decorative images `alt=""`. Always provide intrinsic width and height. Use `loading="lazy"` for below-the-fold content; reserve eager loading for visible, high-priority media such as a header mark or LCP image.

For an asset in `src/assets`, import it and let Astro derive dimensions. Public-directory assets are string paths, so `width` and `height` are required. The configured SVG brand assets follow this public-asset pattern in `Header.astro`.

## Metadata and JSON-LD

Do not build document-head metadata in individual pages. Use `BaseLayout`:

```astro
---
import BaseLayout from '../layouts/BaseLayout.astro';

const structuredData = {
  '@context': 'https://schema.org',
  '@type': 'Article',
  headline: 'A precise, visible article headline',
  description: 'A description that matches the visible article.',
  mainEntityOfPage: 'https://example.com/article/',
};
---

<BaseLayout
  title="A precise, visible article headline"
  description="A description that matches the visible article."
  image="/images/article-social.jpg"
  ogType="article"
  structuredData={structuredData}
>
  <article>…</article>
</BaseLayout>
```

`BaseLayout` passes `structuredData` to `src/components/seo/JsonLd.astro`, which serializes it into an `application/ld+json` script and escapes unsafe markup delimiters. It accepts one Schema.org object or an array for multiple valid graphs. JSON-LD is emitted only for indexable pages.

Schema must be true, page-specific, and consistent with visible primary content. Choose the narrowest truthful type: `Organization` for the organisation's homepage or about page, `Article` for an actual article, `FAQPage` only when the matching questions and answers are visible, and `BreadcrumbList` only when visible breadcrumbs are present. Do not add fabricated reviews, ratings, prices, events, or FAQs. Validate schema after deployment with Google's Rich Results Test and Schema Markup Validator.

## Review checklist

Before merging a public-page change, confirm:

- [ ] One `h1`, a sequential heading outline, and no duplicate main landmark.
- [ ] Sections, articles, navigation, lists, definitions, tables, and contact data use their native elements.
- [ ] Links navigate and buttons act; forms retain native labels and a non-JavaScript path.
- [ ] Metadata is supplied via `BaseLayout`; image dimensions and alt text are correct.
- [ ] JSON-LD, if any, accurately reflects visible content and the page is indexable.
- [ ] `pnpm run verify` and relevant `pnpm run test:e2e` tests pass.
